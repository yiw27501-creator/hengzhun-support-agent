# 售后 Agent：人工纠错规则与 Prompt V1/V2 实验

日期：2026-09-15。状态：真实模型 API 小样本开发集实验；不是线上 A/B 测试。

## 1. 产品决策

用户明确提出：先由人工寻找客户原话、确认客户需求，确认属于模型问题后及时更正。

落实为：客户原话与结构化偏好矛盾时，暂停自动处置并建议转人工；人工核对原始对话、时间和当前需求后修正任务。不能仅凭冲突判定模型出错，也可能是字段过期、抽取错误或客户改变主意。

单个任务的纠正与全局 Prompt 更新分开：确认事实后及时纠正当前建议；经归因确认的模型错误进入错误集，修改 Prompt 后回归验证再考虑发布。当前仅实现模型建议与实验规则，未实现人工工作台、联系客户或业务执行。

## 2. 实验设计与数据修订

- 假设：显式核对字段值、强调冲突升级人工和库存必要条件，可以修复 V1 的已知错误。
- 原开发案例包含“拒绝替代品”字段与“可以换同档商品”原话相矛盾的输入；旧退款标签不再适用。保留这一输入作为冲突案例，标签修正为 escalate。
- 普通退款案例的偏好字段改为 false，避免将无意的数据冲突混入普通退款测试。
- 两组均使用修订后政策 p2-human-conflict 和数据 d2-human-conflict；不是拿旧数据的 V1 与新数据的 V2 比较。
- 数据哈希均为 25d74d800cf52fb3c690bbf69513fbcafe9e260e28238d7288cd8b8af7aa47db。
- 模型 deepseek-flash，thinking disabled，temperature 0，max_tokens 600；同一组 5 条合成开发案例，各运行一次，共 10 次真实 API 调用。唯一有意改变的实验因素是 Prompt。
- V2 增加冲突检查、stock > 0 与价格约束、动作参数一致性检查。不要求输出内部推理过程。

## 4. 证据与局限

- V1：results/20260915T025811723991Z/，含 config.json、records.jsonl、summary.json。
- V2：results/20260915T030002945918Z/，含相同文件。
- 原始首轮实验 results/20260915T023844495736Z/ 保留，不覆盖。
- 本地评分器单元测试 8 项通过；不等于业务链路测试通过。
- 自动评分检查动作、金额、SKU、格式和证据 ID；不能完整衡量解释忠实性、客户满意度或真实解决率。
- V2 针对已看到的开发集错误修改，5/5 不证明泛化或生产可靠性。当前 holdout 为相同模板轻微改值，也不足以作为独立泛化证据。
- 尚未测试所有政策优先级组合；应增加独立编写的多轮对话、偏好变更时间、否定表达、提示注入、事实缺失和风险组合案例，并重复运行。
- 库存、金额、支付等硬约束上线时还应由服务端确定性校验兜底，不能只依赖 Prompt。本次未实现该业务执行防线。

## 5. AI 产品经理的实际贡献及后续验收

本次用户贡献是确定人工介入边界和纠错原则；实验将该决策转化为政策、标签和可验证的 Prompt 变更。可以描述为“我定义冲突处理规则，参与错误归因与验收标准设计，通过控制变量的开发集实验验证修改方向”，不能声称自己训练了模型或上线了全自动退款系统。

后续人工纠错闭环应记录 task_id、原始消息引用与时间、模型及 Prompt 版本、原建议、确认后需求、修改后建议、归因、处理人和时间。先确认错误来源，再分别处理数据修正、规则调整或 Prompt 修改；保留审计记录，回归未通过不发布新版本。
