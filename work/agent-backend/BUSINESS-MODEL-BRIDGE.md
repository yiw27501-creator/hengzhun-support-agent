# 缺货服务台真实模型联动（2026-09-17）

## 本轮真正接通的链路

`/service` 原话输入 → POST `/api/workflow/business/{task}/chat` → 同事务保存消息、撤销旧授权 → 预留持久化预算 → 官方 DeepSeek 返回 tool/quote → 服务端结构/原文证据校验 → 白名单模拟只读工具 → 事实模板回复与同一任务方案 → 客户明确点击确认 → 规则引擎校验 → 恢复队列 → 沙箱执行回执。

不是模型直接授权退款；不是供应商原生function-calling协议，而是受限JSON工具路由。查询真实模型，业务工具仍模拟。新消息与旧结果版本冲突时结果SUPERSEDED，不覆盖新授权。请求ID用于防重复调用，调用失败不自动付费重试。现阶段请求同步、网络在事务外；若进程在调用过程中中断，PENDING不会自动恢复，需要人工排查或新请求，不能宣称有完整持久化模型作业恢复。

支持 inventory/purchase/product/clarify/pause/human/refund_offer。模型只选只读查询或交互路径；固定模板依赖工具事实形成答复，未让模型二次自由生成。历史客户消息与此前已完成的Agent回复进入上下文，最多30条/12000字符，超限拒绝。

## 开启（会产生模型费用）

```powershell
python server.py --desktop --async-jobs --business-model --key-file ../model-experiment/.env --direct --max-model-calls 3 --port 8775 --db data/business-model-demo.db
```

密钥不写入源码、页面或记录。默认不带business-model时仍为零费用规则演练。business-model要求规则执行规划器，避免一条交互隐式再触发其他付费规划。每次发送最多1次请求，预算按该队列数据库累计，重启不清零；批量生成规则工单不消耗模型请求。当前界面顶部显示真实对话、规则执行及余额。

打开库存待核实工单，在“客户原话 → 模型理解 → 工具核验”输入合成消息。初次工单已有规则准备步骤，不把它冒充模型触发；新输入提交后才是真实模型路由。

## 测试与边界

test_business_chat.py覆盖模型替身的路由→工具→确认→队列→回执；同request_id不重复调用；非法工具失败闭锁；慢结果被新消息作废；预算不足/未开启拒绝；暂停和购买记录查询不能授权。

自由文本桥接目前仅支持缺货相关工单，已签收退货仍使用原结构化流程。代买身份验证和购买人授权仍是模拟按钮；不能因此认为已经接入可信客户身份。没有接入商家外部API或生产回调。没有本轮RAG/FAQ检索扩展，也没有模型连续自主循环执行多个工具；这些仍需另行集成与评测。对现有业务页来说，这是打通一个受约束的真实模型入口，而非全部Agent能力完成。
