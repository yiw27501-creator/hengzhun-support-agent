# 产品定位与自动化契约

## 谁使用，谁受益

核心产品为 B 端售后工作台。目标客户假设是存在缺货处置需求的中小电商商家，不按未调研的订单规模或收入虚构精准画像。直接使用者为售后客服、运营和知识维护者；受益者是购买者。客户入口展示 B2B2C 的购买者接触面，不是第二款独立 C 端产品。

价值假设：减少核对订单和重复操作的时间，降低客户改口后误执行风险，使异常处理有证据可查。暂无商家访谈或真实收益证明。

## 场景与非目标

主场景：已支付缺货订单 → 明确退款/换货诉求 → 核对事实和有效授权 → 执行 → 回执核验。
异常：客户改口、需求歧义、无库存、身份/支付不明、金额超限、工具响应丢失。
非目标：真实支付、多动作赔付与补发、退货物流拦截、全品类通用客服、跨商家生产平台。

## 入口信息架构

- /：产品适用对象、业务场景、边界、客户体验/运营分流。
- /customer：创建合成缺货订单、提交原话、回复澄清、叫停、查看状态。只保留本次浏览器会话中的任务 ID。
- /lab：核对同一任务的原话、版本、授权，提交执行、查看回执。
- /knowledge：政策/FAQ 审核、发布和撤销。
- /quality：异常归因、固定评测、发布记录。
- /workbench.html：保留早期基础演练，不作为默认入口。

没有伪造登录界面。这些入口共用本机演示会话，任何本地操作者可以切换角色；不能向公网开放或录入真实客户隐私。生产版必须由真实渠道身份映射订单，不能仅靠页面隐藏按钮保护 API。

## 自动处理资格

| 情况 | 处理 | 授权依据 |
|---|---|---|
| 询问政策/到账时间 | 有适用知识则解释，否则说明未知 | 不产生财务授权 |
| 模糊诉求、多选或条件未核实 | 澄清，禁止执行 | 不根据模型标签推断同意 |
| 新客户消息/改口 | 旧授权失效，重新核对 | 当前消息版本 |
| 已验证明确意愿且满足身份、支付、库存、金额条件 | 可执行沙箱动作 | 结构化有效授权，不是 LLM 自我判断 |
| 超限、库存失效或风险不明 | 转人工 | 人工也不能绕过硬规则 |
| 已有成功回执 | 查询核验，不重复执行 | 稳定订单业务回执 |

当前购买者输入由本机模拟，新的自然语言诉求仍由运营核对授权。没有实现可信客户渠道的全自动授权。规则演练预置的有效授权与新客户消息的授权路径不同，必须说明。

## 状态与撤销语义

对话状态（理解/澄清/暂停）、业务授权、执行状态是三个维度，不强行塞进单一标签。UI 展示是当前持久化事实的投影，不表示新增了所有生产状态。

- 排队或规划中：新消息会使旧授权失效；执行前核对快照和消息版本。
- 本地事务中：叫停与提交按 SQLite 写锁串行化。先完成业务提交则叫停返回冲突，不能承诺已撤销。
- 已执行但响应丢失：数据库回执存在，先对账；不能仅按队列失败判断业务未执行。
- 已执行：客户入口禁止追溯撤销，后续处理需新业务流程。
- 真实外部请求已发出但状态未知：当前未接入；未来必须有 RESULT_UNKNOWN、查询回执与人工核验，不虚构可中断。

本轮增加本地政策执行栅栏：规划时政策集合哈希与执行前生效集合一致才允许进入业务事务；短事务期间锁住知识发布写入。政策撤销若先完成，旧方案被拒绝。仅约束同机 SQLite 沙箱，不保证外部支付分布式原子性。

## 后续业务验证方案（尚未执行）

招募 3–5 位目标售后人员，给出相同合成场景，观察无需提示能否定位订单、辨别授权、处理撤回与超时。记录任务完成率、关键误操作数、完成时间；同时记录样本角色与经验，不将小样本推成行业结论。

若能联系一家商家，先做匿名历史工单回放和人工基线，再影子运行，不直接放开真实财务操作。访谈不可替代行为测试；模拟分布不可冒充真实业务分布。
