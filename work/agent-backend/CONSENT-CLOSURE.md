# 消息版本与授权撤回迭代 · 2026-09-16

## 本轮实现

- 将模型规划移出 SQLite 写事务，避免模型等待期间客户撤回消息无法提交。
- 执行阶段重新读取事实，旧规划快照与当前事实不一致时不能执行。
- 新增 task_messages 持久化表，按任务绑定消息 ID 和递增版本。
- 新增 POST /api/workflow/tasks/{id}/messages：message_id、text、expected_version。
- 消息入库、清除旧授权、暂停任务与审计记录在同一事务完成。
- 同一消息 ID/内容/前置版本重复提交幂等；冲突内容或过期版本返回 409。
- 人工确认须同时匹配最新 message_id 与 expected_version。授权记录 authorized_version；执行规则再次校验。
- 已产生业务回执时拒绝追溯撤回，不伪装成已撤销，也不再次执行。
- 实验台新增当前订单的客户消息入口，可在后台规划期间提交。

## 演示

1. 创建“正常换货”任务，先不提交执行。
2. 在页面底部提交“先别退款，我再想想”。任务变为 WAITING_HUMAN，旧授权清空。
3. 再提交“想好了，确认退款”。消息版本递增，仍需核对当前意愿。
4. 在人工核对区选择退款并填写核对依据。确认绑定当前版本。
5. 提交异步处理，完成沙箱退款，查看回执与 consent.invalidated / human.confirmed / result.verified 轨迹。

并发时序由自动化测试验证：阻塞规划器 → 提交叫停消息 → 释放规划器 → 旧方案被拒绝且无执行回执。

## 验证

44 项单元/集成回归通过；JavaScript 语法检查通过。本轮没有付费模型调用，使用可控规划器验证并发顺序，不把随机网络时延当作并发正确性测试。

## 边界与下一步

- 当前客户身份仍由本机操作者模拟，没有真实客服渠道签名或客户/订单身份验证接入。
- 所有新客户消息保守地撤销授权，即使只是“谢谢”；这是安全优先的 POC 策略，可能增加人工介入。
- 原始对话提取模块尚未自动授权本订单；人工确认不是模型推断。下一步接入有版本约束的理解结果与澄清轮次。
- 只有已提交数据库事务的消息能阻止后续提交的业务效果。若执行事务先提交，新消息不能撤回已发生的效果；分布式支付还需要取消协议和补偿机制。
- 当前幂等约束可避免重复沙箱效果，但并发工作者仍可能重复规划或产生模型费用；不能称为模型调用恰好一次。
- 没有更新云端、执行真实支付或发布 GitHub。
